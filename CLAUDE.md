# crimson-rs — Crimson Desert Archive Toolkit

Rust library with Python bindings (via PyO3/maturin) for reading, writing, and modding Crimson Desert game archives. **Personal-playground fork — not intended to flow back to the `potter420/crimson-rs` upstream.** Supports Crimson Desert 1.05–2.06 across the PALOC / PAZ / PAMT containers and the save format. The iteminfo, skill and table parsers target the **latest patch only** — currently 2.06, byte-perfect on 7,068 base + 8,218 `dlc_01` items (verified on the live 2.06 install, 2026-11-27).

⛔ **Every `CLAUDE.md` stays ≤ 40 KB (40,960 bytes), and this one as small as it can be.** It is loaded on every turn, so each line costs on all of them. History goes in [`docs/dev-log.md`](docs/dev-log.md), per-patch detail in [`docs/validated-patches.md`](docs/validated-patches.md), and a new document gets its row in [`docs/README.md`](docs/README.md), not here. Over the line, move or trim; never grow. `claude_md_files_stay_under_40_kb` (`cargo test --lib`, so CI) fails on any `CLAUDE.md` past the limit.

Current layout facts (what each patch changed and how it was pinned: [`docs/validated-patches.md`](docs/validated-patches.md)):

- **2.06 row head** (paver `2/6/0`): every `.staticinfoheader` lists `[key][u32 len][name][u32 offset][u32 size]` per row and every body row opens `[key][u32 row index]` (`binary::static_header`). iteminfo, skill and stringinfo read it directly; every other table parser rebuilds the pre-2.06 layout in memory (`static_header::legacy_pair`). The eight body-only bridges need `*_load_from_bytes_with_header`. 2.06 also inlined anonymous conditions as `01` + bytecode in ten tables ("Inlined conditions (2.06)" in [`scripts/CLAUDE.md`](scripts/CLAUDE.md)).
- **A patch-level update can change a layout** (2.04.08 and 2.05.01 did): run the suite on every Steam update, not only on minor bumps.
- **DLC:** `dlc/dlc_01/` is a second install root (Steam depot 5001841, DLC app 5001840, installed only for owners). Nothing merges it automatically; the bridges that can merge it do so only when the caller asks (`*_merge_dlc_from_bytes`, [`docs/c-abi-surface.md`](docs/c-abi-surface.md)), and every function works without it.
- **Save bodies carry absence markers:** one `0x01` byte per absent dynamic array or object list ("Absence markers" in [`docs/c-abi-surface.md`](docs/c-abi-surface.md)). Save schemas move per patch; elements cross patches through the name-keyed element templates (`src/c_abi/element_template.rs`).

What carries forward to every future patch:

- **Archive paths are resolved, never hardcoded.** Every library entry point takes its directory from the caller. The gamedata / PALOC layout lookup lives in [`scripts/gamedata_layout.py`](scripts/gamedata_layout.py) and `src/binary/gamedata_layout.rs` (test-only), both newest-layout-first with fallback — a new layout is one entry at the front of each list.
- **`PARSER_TARGET_GAMEDATA_MAJOR` / `_MINOR` are read as a pair** — the minor resets on a major bump (paver `2/0/0` followed `1/18/0`) — **plus `PARSER_MIN_GAMEDATA_PATCH`** since a layout moved inside minor 4, and again inside minor 5. Current: 2.06, patch ≥ 0, paver `2/6/0`. Reset the patch floor to 0 when the minor moves.
- **When values line up, the layout may still be wrong.** On 2.04 a list that is empty in the base table looked like a one-byte flag until `iteminfo.dlc_01` populated it. Check a new layout against every table that shares it, DLC included.
- **A new field inside an all-zero run can't be located by byte diff** — every candidate position round-trips. Settle it by which reading keeps the neighbours' known value distributions intact, and diff against the kept previous-version binary in `gamedata-bin/` before arguing from statistics.
- **The 3-byte `..._lookup_slot_mask` C ABI is a partial read** since the 2.01 dye-mask widening; the 12 bytes are one flag per dye slot number (the save's `_dyeSlotNo`), read through `..._lookup_dye_slot_bits` / `..._lookup_slot_mask_full`, and an item reaches its dye rows through its `.prefab` meshes (see [`docs/dye-editor-scope.md`](docs/dye-editor-scope.md)).
- **Curated quest tables are keyed and tested** — `curated_titles_match_live_install` fails on the next retitle.

Previous-version parsers: use the `git archive HEAD` + `maturin build` + `pip install --target` route in [`scripts/CLAUDE.md`](scripts/CLAUDE.md) ("Sibling-parser").

This file is intentionally a **minimal index** — detailed reference lives in the linked docs.

# Development
- **Build (Python wheel):** `maturin develop` (in a venv; the project uses `.venv/`) — auto-activates the `python` feature via `[tool.maturin]` in `pyproject.toml`. **The venv must be Python 3.12** — the wheel builds `abi3` for Python ≥ 3.12, so create `.venv` from a 3.12 interpreter (`py -3.12 -m venv .venv` or `C:\Users\<you>\AppData\Local\Programs\Python\Python312\python.exe -m venv .venv`), `source .venv/Scripts/activate`, then `maturin develop --release`. Run `export_for_ce.py` / any parsing from this same venv. **Stale-build gotcha — check this FIRST on a new patch, before suspecting schema drift.** Two independent copies can go stale: (a) a stray `crimson_rs` in the *global* Python 3.12 `site-packages` from an earlier `pip install`, and (b) **the venv's own `.pyd`** — `maturin develop` installs `crimson_rs` as editable, so `crimson_rs.__file__` points at the in-tree `python/crimson_rs/__init__.py` and *looks* current while the sibling `python/crimson_rs/crimson_rs.pyd` is whatever was last built. On 2026-08-09 that `.pyd` was 30 days old (a 1.13-era build) on a tree at 1.16. Either one silently mis-parses a new patch. So: `maturin develop --release` **before** any parsing run on a fresh patch, and sanity-check with `python -c "import crimson_rs, pathlib; p=pathlib.Path(crimson_rs.__file__).parent/'crimson_rs.pyd'; print(p.stat().st_mtime)"`. If you maintain the global install too, refresh it with `<Python312> -m pip install --force-reinstall --no-deps target/wheels/crimson_rs-*.whl`.
- **Build (C# / native):** `cargo build --release --features c_abi` → `target/release/crimson_rs.dll` (cdylib, ~1.2 MB) **and** `crimson_rs.lib` (staticlib, ~15 MB) in one pass. PyO3 is **not** linked; [`.cargo/config.toml`](.cargo/config.toml) statically links the MSVC CRT so the dll has zero transitive DLL deps. Downstream integration recipe (LoadLibrary vs NativeAOT single-file): [`docs/c-sharp-nativeaot-integration.md`](docs/c-sharp-nativeaot-integration.md).
- **Feature flags:** `default = []` (bare pure-Rust core, no FFI; dead_code allowed crate-wide via `cfg_attr` in `src/lib.rs`), `c_abi` (extern "C" surface), `python` (PyO3 abi3 + `extension-module`: no libpython link on Linux/macOS; on Windows the `.pyd` imports only the stable `python3.dll`). The two consumer features are independent and composable — enable both for the maximum surface (what CI lints).
- **Test:** `cargo test --lib --features c_abi -- --test-threads=4`, which is what CI runs. Without `c_abi` only 111 of the 399 tests compile in.
- **Lint:** `cargo clippy --all-targets --lib --features c_abi,python -- -D warnings` (the union-of-all-features gate; CI also runs `cargo check --lib` for the bare-default build, see `.github/workflows/ci.yml`; `main` is branch-protected on the strict clippy check). **Local gotcha:** the `python` feature pulls PyO3 `abi3-py312`, so this aborts with `cannot set a minimum Python version 3.12 higher than the interpreter version 3.11` when the ambient `python` on PATH is older than 3.12 — prefix it with the 3.12 venv interpreter. **`PYO3_PYTHON` must be an ABSOLUTE path**: the pyo3 build script runs the interpreter from its own working directory, so a repo-relative `.venv/Scripts/python.exe` fails with `failed to run the Python interpreter at .venv/Scripts/python.exe (os error 3)` in both PowerShell and bash. Use `PYO3_PYTHON=D:/Github/crimson-rs/.venv/Scripts/python.exe cargo clippy --all-targets --lib --features c_abi,python -- -D warnings`. CI is unaffected (it uses the Ubuntu runner's Python 3.12; the workflow does not pin it); the `c_abi`-only build has no PyO3 and needs no Python.
- **Workflow:** develop on `dev` → PR to `main` → CI green → merge. That's the whole loop — **there is no publish step.** `.github/workflows/ci.yml` (clippy + cargo test) is the only workflow and the required check on `main`. The old `build.yml`, which rebuilt a Windows wheel on every push to `main` and republished it as a rolling `v1.0.<minor>.x` "Development Build" pre-release, was removed 2026-08-09 — traffic showed no external consumers, so there is nothing to bump on a new patch series and no release to retire. Consumers build from source (`maturin develop --release` for the wheel, `cargo build --release --features c_abi` for the native dll/lib). **Fork gotcha:** this is a fork of `potter420/crimson-rs`, so `gh` defaults PRs to the *upstream* parent (they fail with "No commits between main and dev / Head ref must be a branch"). Run [`scripts/setup-fork-guards.ps1`](scripts/setup-fork-guards.ps1) **once per clone** (pins `gh repo set-default bbfox0703/crimson-rs`, `remote.pushDefault=origin`, removes the `upstream` remote, and installs a `pre-push` hook that refuses any push to `potter420/crimson-rs` however it is addressed — the upstream is a ~1.03-era parent with nothing to send it), or always pass `gh pr create --repo bbfox0703/crimson-rs`. Never PR/push to upstream.

# Rules
- Ask before adding new dependencies to Cargo.toml.
- Binary format must roundtrip (read and write back identically).
- Custom types for binary serialization: `CString` (u32 len + len bytes — NO trailing NUL; this is what `iteminfo.pabgb` uses), `BString`-shape (u32 len + len bytes + u8 NUL terminator — the PAPGT group_names_buffer; skill entry names have been plain `u32 len + bytes` since 2.04, the byte after them is `EntryHead::unk_post_key`), `optional<T>` (u8 flag + T if nonzero), `array<T>` (u32 count + count × T), `Variant` (u8 tag + match on tag).

# Working conventions
The maintainer works on two Windows PCs. These rules used to live in one machine's Claude memory; they are here so both clones share them. Machine and archive specifics (archive paths, the Steam manifest, reading the Google Drive archive) are under "Machine notes" in [`scripts/CLAUDE.md`](scripts/CLAUDE.md).
- **Shared knowledge goes in the repo, not in Claude memory.** Memory is per machine (`~/.claude/projects/…`), so the other PC never sees it. Put a new working rule here, an engineering note or machine path in `scripts/CLAUDE.md`, and keep memory for notes about that machine alone (which PC it is). When asked to tidy memory, move anything shared into these files.
- **Verify a root cause before stating it, and re-check when the maintainer questions it.** They have been right each time they doubted a diagnosis: a "game loader bug" that was a crimson-rs encoder relocation bug (a no-op decode → encode round-trip never moves a block, so it cannot catch relocation bugs); a suspect field that turned out to be present on all 490 items; a 2.01 layout argued from value distributions that one tandem walk against the kept 2.00 binary reversed. Decode the bytes, count occurrences or build a controlled repro, say how sure you are, and look for a ground-truth baseline (the version archive, a kept save) before arguing from statistics. Don't call something unavailable without checking where it would live.
- **Every PR adds a [`docs/dev-log.md`](docs/dev-log.md) entry**, newest first, as the PR's last commit: what changed and why, what was measured, what is still not established, the test count, and whether CrimsonAtomtic must act. Never rewrite an old entry; correct it in a new one. A typo-only doc fix needs none. The file's header has the format and the split rule.
- **Commit, push, open a PR or merge only when asked.** After a commit, check `git show --stat HEAD`: on 2026-11-13 a `git add` whose path differed from the tracked file only in case matched nothing, and the PR merged without its README.
- **Merging:** the repo does not allow auto-merge, and `main` requires "clippy + cargo test". Don't poll CI; the maintainer says when it is green. Then confirm `gh pr checks <n> --repo bbfox0703/crimson-rs` passes and `gh pr view <n> --json mergeStateStatus` is `CLEAN`, and run `gh pr merge <n> --repo bbfox0703/crimson-rs --merge --match-head-commit <head sha>`.
- **Downstream:** the C# editor (`CrimsonAtomtic`) refreshes its vendored crimson-rs copy itself; don't edit that repo from a crimson-rs session. Doc-only changes need no downstream notice.
- **Mods on 2.04+:** don't state that `pack_mod` output loads in the game, and don't try to get around the PAPGT signature-like trailer.
- **Live-game RE:** reading the running game's memory read-only (`ReadProcessMemory`) is fine. That is how the 2.05 item key array was found. Never write to the process.
- **Tell version binaries apart by hash, never by size.** `iteminfo.pabgb` was 5,938,891 B in 1.13.01, 1.14 and 1.15 alike.
- **A per-version archive missing on one PC is not lost.** The archives are split across the two machines, so ask before concluding one is gone, and don't "correct" docs that name an archive this machine lacks.
- **When the other PC has done a patch:** `git pull`, then `maturin develop --release` before any parse (the stale-`.pyd` trap under Development). Run `scripts/setup-fork-guards.ps1` once on each clone, and clone `bbfox0703/crimson-rs-private` next to it once (the save fixtures; see Reference Files).
- **Code comments** say what the code does and why, in the present tense. **No history** in a comment: no fix narrative ("used to", "before the fix"), no audit / review tags, commit hashes, PR numbers or "found on <date>"; that goes in `docs/dev-log.md` (or the document it points to). **No line numbers into this repo**: name the function, type or section. Don't restate the next line, don't enumerate callers or fields that must be kept in sync, no "only" / "every caller" claim without a test behind it, no plan wording ("will", "v2"). Facts about the game data are fine when they are the reason for the code; counts that pin a patch belong in a test or the dev-log. `repo_doc_budget::comments_cite_no_lines_or_audit_tags` (CI) fails on line references and audit tags.
- **Line endings:** `core.autocrlf=true`. `sed -i` over a CRLF file silently rewrites it LF, so edit with the Edit tool or a script that keeps the file's line endings. Compare key snapshots by content (`tr -d '\r'`), never by hash.
- **Long test runs:** `cargo test … | grep` prints nothing if the process dies. Redirect to a file and tail it.
- **Test data:** treat the local version archives (`X:`, `G:`) as volatile: they can disappear at any time, so no test may depend on them. Any per-version data a test needs gets a copy in `crimson-rs-private` (`saves/`, or `gamedata/<ver>/` read through `test_fixtures::save` / `test_fixtures::gamedata`), limited to what the tested pattern needs (the files or rows that exercise it, not a whole bin folder), and the test skips when the file is missing.
- **A tripped heuristic pin is not automatically a drift.** Check that every row parsed (row count equals the header count), that the `KNOWN` pins pass and that the value distribution looks sane before touching a parser. A byte-identical round-trip doesn't prove the field boundaries either.

# Binary Exploration
- For a first look at an unfamiliar binary, write partial `.hexpat` patterns in `references/` and iterate with `plcli run -i <file> -p <pattern.hexpat> -v -d`.
- For cross-version drift, use the tandem-walk / `diff_<old>_<new>.py` workflow and the Rust `_probe_*` tests in [`scripts/CLAUDE.md`](scripts/CLAUDE.md) — they diff two versions, which a pattern file can't.

- `out/baselines/1.05/items.jsonl` — Per-version reference data (gitignored — keep local).
- `D:\Github\crimson-rs-private\saves\` — Real save files the tests use as fixtures (1.09, 1.10 and the 1.10 length-change repro sets), in the **private** `bbfox0703/crimson-rs-private` repo, cloned next to this one on each PC (override with `CRIMSON_FIXTURES_DIR`; resolver in `src/test_fixtures.rs`). Fixture tests skip without it, and CI never has it. Until 2026-11-27 they sat in `tests/fixtures/saves/` under git-crypt; commits before that still hold the encrypted blobs (and `tools/git-crypt.exe` stays for them). `*.save` is gitignored here: never commit a save to this public repo.
- `D:\Github\crimson-rs-private\gamedata\` — Decrypted static-info tables of older versions the tests need (the skill tables of 2.04, 2.05.01 and 2.06 for the cross-version round-trip); its README lists each file's hash and the tests that read it.

# Module map
`src/` is organized as: `binary/` (PAMT/PAPGT/PAZ/PALOC/trie/paver container formats + the test-only `gamedata_layout` archive-path resolver), `crypto/` (Jenkins checksum + ChaCha20), `item_info/` + `skill_info/` + `string_info/` + `character_info/` (byte-roundtrip parsers), `save/` (save header + crypto + body), and `c_abi/` (the feature-gated extern "C" surface). The full annotated per-file map is in [`docs/c-abi-surface.md`](docs/c-abi-surface.md).
