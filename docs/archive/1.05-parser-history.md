# Crimson Desert 1.05 ItemInfo parser — RE history

End state (2026-05-07): **6,236 / 6,236 (100.0%) perfect parse**, byte-perfect roundtrip on every item via `serialize_iteminfo`.

This doc is the long-form story of how the 1.05 ItemInfo parser was reverse-engineered. The currently-correct schema is documented in [`../scripts/CLAUDE.md`](../../scripts/CLAUDE.md). This doc exists so that the next session can understand *why* the schema looks the way it does, what was tried, and what to avoid.

## TL;DR — the 1.05 schema delta

Compared to 1.04, the only schema differences are:

1. **`ItemIconData` grew by 5 bytes per entry** — a new `icon_path_alt: StringInfoKey` between `icon_path` and `check_exist_sealed_data`, plus a trailing `unk_flag: u8` after `gimmick_state_list`.
2. **A new 5-byte block** (`unk_pre_pattern_key: u32 + unk_pre_pattern_flag: u8`) inserted between `convert_item_info_by_drop_npc` and `pattern_description_data_list`. The u32 is always 0 in observed data; the u8 is `1` only for the 48 fish-food items (`Food_Salmon`, `Food_Trout`, `Food_Carp`, …) — looks like a recipe / cookable-flag pair added with the 1.05 cooking expansion.
3. **`SubItem` accepts a new tag value `15`** (treated as the existing `None` variant — both 14 and 15 carry no payload).

That's it. Nothing else moved. What looked initially like a much more invasive layout change was either (a) a misinterpretation that round-tripped by coincidence on some items, or (b) an artifact of the anchor scanner.

## Phase 1 — the wrong "variant tail" model (don't repeat)

The first iteration of 1.05 RE found that some items had bytes after `max_endurance` that didn't fit the 1.04 schema. The hypothesis was a *variant tail* — a CString `new_icon_path`, then a conditional branched body for ammo items, plus a `unk_pre_repair_*` sentinel. With this model, ~5,400 / 6,236 items round-tripped (86.9%).

The model was wrong. It happened to round-trip on items where the misread bytes coincidentally satisfied later parser checks (e.g. ammo items where `max_endurance == 0xFFFF` provided a bogus "trailer sentinel"). On the 800+ items that didn't coincide it broke parsing entirely.

Scripts that validated and then dis-proved this model are in [`../scripts/archive/`](../../scripts/archive/):
- `probe_new_layout.py`, `dump_post_bytes.py`, `refine_discriminator.py`, `debug_post31.py`.

**Lesson:** A schema model that round-trips on most items but fails catastrophically on a minority is almost always wrong. Don't trust statistical "fits" — find a binary discriminator in the *data*, not in the parser's tolerance for ambiguity.

## Phase 2 — 1.04-anchored cross-version diff (got to 99.7%)

The fix came from anchoring against a known-correct 1.04 parser:

1. **Extracted `out/baselines/1.04/iteminfo.pabgb`** from the maintainer's 1.04.01 game install via `crimson_rs.extract_file(..., "0008", "gamedata/binary__/client/bin", "iteminfo.pabgb")`.
2. **Built the historical 1.04 parser** as a sibling install — `git worktree add ../crimson-rs-104 56a57da`, `maturin build --release`, `pip install --target=.crimson_rs_104` so it could be `sys.path`-loaded without colliding with the in-tree 1.05 wheel. See [`historical-parser-setup.md`](../historical-parser-setup.md) for the recipe.
3. **Dumped `parse_iteminfo_tracked` spans** for representative items via [`../scripts/archive/dump_104_spans.py`](../../scripts/archive/dump_104_spans.py), writing every named 1.04 field's start/end offset to `out/baselines/1.04/spans.json`. The 1.04 parser is correct on its own data, so its tracked spans are ground truth.
4. **Cross-aligned 1.04 spans against 1.05 chunks** via [`../scripts/archive/align_104_105.py`](../../scripts/archive/align_104_105.py). For each 1.04 field, search for the same byte sequence in the 1.05 chunk; the offset delta is the cumulative shift. The shift transitioned 0 → +5 across `item_icon_list[0]` (the known `ItemIconData` growth) and +5 → +10 right after `convert_item_info_by_drop_npc` for items where the next field (`pattern_description_data_list`) was non-empty enough to disambiguate.
5. **The 5-byte block at the +5 → +10 transition** was `00 00 00 00 00` for 4,257 items and `00 00 00 00 01` for the 48 fish-food items. Confirmed by [`../scripts/archive/probe_new_5b_field.py`](../../scripts/archive/probe_new_5b_field.py). Modelled as `unk_pre_pattern_key: u32 + unk_pre_pattern_flag: u8`.
6. **Removed the (wrong) variant-tail / `ammo_mid_block` / `ItemInfoTail`-prefix model** and restored the 1.04 trailing fields verbatim.

After this fix: **6,215 / 6,236 (99.7%) perfect**, with 7 `leftover:N` and 14 `fail:<path>` clusters surviving. Both clusters were initially (incorrectly!) interpreted as new schema features.

## Phase 3 — the 21 stragglers were an anchor-scanner bug, not schema drift

The 7 `leftover` items had 54, 88, or 93 bytes appended after the parser's last consumed field (`repair_data_list.__count__`). The 14 `fail` items had numeric string_keys (e.g. `4295766159917168`) and broke parsing mid-item. A natural reading was "1.05 added another field that's only present on some items, and the new items are dev / placeholder records with a different schema."

That reading was wrong. What was actually happening:

- The "trailer" bytes appended to a `leftover` item's chunk were **the start of the very next item** — a copy of the next item's first ~50 bytes embedded into the previous item's chunk. Specifically, the trailer contained `key + ASCII string_key + is_blocked + max_stack_count + item_name.{category, partial index}` — exactly what an `ItemInfo` record begins with.
- The 14 `fail` items' chunks were **the rest of the next item starting from byte ~50**, with their first bytes being a *duplicate* `key` value that happened to be a 16-digit numeric string in the binary. The numeric string was actually an inner CString field (`item_name.default` of the ASCII record), not a top-level item start.
- The duplicates existed because items in 1.05 carry an in-binary fallback name in `item_name.default` (used when paloc has no localized name). For the 71 dev/QA items with no paloc translation, that fallback name is a 16-digit numeric paloc lookup index encoded as a string. That numeric string passes the anchor scanner's "looks like a string_key" check.

The root cause was in [`../scripts/build_items_jsonl.py`](../../scripts/build_items_jsonl.py) `looks_like_item_start` and three duplicate copies elsewhere. Two checks were too strict:

```python
# Before                            # After
if not (2 <= slen <= 64): ...       if not (2 <= slen <= 128): ...
# is_ident_byte:                    # is_ident_byte:
ascii word chars / _ / space        ... or b >= 0x80   # accept UTF-8
```

`slen <= 64` rejected names like `Item_Skill_AbyssGear_AddCriticalRateByMaterialKey_LeatherArmor_LV1` (66 bytes), `..._FabricArmor_LV1` (65 bytes), and `Recipe_..._PlateArmor_LV1` (71 bytes). The ASCII-only `is_ident_byte` rejected UTF-8 multi-byte sequences in 1.05 string_keys like `Goblin_Merchant_Fabric_Armor_Ⅲ` (the Roman numeral Ⅲ is 3 bytes of UTF-8).

When the scanner rejected the *real* (long-or-Unicode) ASCII anchor, it skipped forward and locked onto the inner numeric duplicate, splitting one item into two malformed chunks.

The 14 items that moved to their correct ASCII anchors after the fix:

| #  | Cluster                                                         | Cause                |
| -- | --------------------------------------------------------------- | -------------------- |
| 6  | `Item_Skill_AbyssGear_…_LeatherArmor/FabricArmor_LV{1,2,3}`     | `slen` 65–66 > 64    |
| 3  | `Recipe_Item_Skill_AbyssGear_…_*Armor_LV1`                      | `slen` 71+ > 64      |
| 5  | `Goblin_Merchant_Fabric_{Armor,Cloak}_Ⅲ/Ⅳ/Ⅵ`                    | UTF-8 Roman numeral  |

Same fix in 4 places: `scripts/build_items_jsonl.py`, `scripts/export_for_ce.py`, `scripts/anchor_diff.py`, and the Rust mirror `src/python.rs::scan_next_item_start`.

## Lessons learned

1. **Sanity-check the anchor scanner before chasing schema mysteries.** The 14 fails / 7 leftovers spent significant RE budget on a non-existent schema feature. The actual root cause was 8 lines in `looks_like_item_start`.

2. **A schema delta that round-trips on most items but fails on a few is *almost always* a wrong model.** Pearl Abyss doesn't usually ship category-specific schema variants — when a parser fits 6,215 items perfectly, the remaining 21 are more likely a data-extraction issue than a schema gap.

3. **CString in this codebase has *no* trailing NUL.** Earlier docs claimed `u32 len + bytes + NUL byte`. The implementation in `src/binary/types.rs::CString::read_from` reads `len` content bytes and stops. The "NUL" the anchor scanner exploits is just the next field's first byte (`is_blocked: u8`), which is almost always `0`. This caused several wrong manual byte-offset calculations during Phase 3.

4. **`parse_iteminfo_tracked` is a list-parser, not a single-item parser.** It loops `while offset + 8 < data.len()` reading successive `ItemInfo`s. Feeding it a single chunk that contains exactly one item produces `spans=[1 item]` with no error. Feeding it a chunk with one item plus trailing bytes produces `spans=[1 item]` *and* an `error_span` from the failed second-item attempt. Several Phase-3 hypotheses were derailed by reading the failed second-item attempt as if it were the first item's "trailer field."

5. **Same key value appears multiple times in the binary.** It's the item's own `key` field, plus every `ItemKey`-typed field in other items that references it (`inventory_info`, `equip_type_info`, `convert_item_info_by_drop_npc`, etc.). Plus the in-binary numeric fallback name (`item_name.default` for dev items) is a 16-digit string that passes the anchor scanner's "looks like a string_key" filter. This is why anchor scanning *must* validate the structural shape, not just match key bytes.
