# crimson-rs — Crimson Desert Archive Toolkit

Rust library with Python bindings (via PyO3/maturin) for reading, writing, and modding Crimson Desert game archives. **Personal-playground fork — not intended to flow back to the `potter420/crimson-rs` upstream.** Supports Crimson Desert 1.05–2.01 across the PALOC / PAZ / PAMT containers and the save format. The iteminfo parser targets the **latest patch only** — currently 2.01, byte-perfect on 6,813 items (verified on the live 2.01 install, 2026-09-04).

**2.01 is a container reshuffle, not a format change.** Pearl Abyss renamed the gamedata directory and every one of its file extensions — `0008/gamedata/binary__/client/bin/<t>.pabgb`/`.pabgh` became `0008/gamedata/binarystaticinfo__/bin/<t>.staticinfobody`/`.staticinfoheader` (the `*.pabgm` misc blob moved to a `bin/misc` subdirectory as `.staticinfomisc`), and each language's single `localizationstring_<lang>.paloc` became 39 per-namespace files under `gamedata/stringtable/binary__/<lang>/`. **Not one byte inside any of those files changed shape** — the PALOC container has no header, so re-serialising the concatenated namespace entry lists reproduces the old blob exactly. The library itself never hardcoded an archive path (every entry point takes the directory from its caller), so this cost zero production code; the resolution lives in [`scripts/gamedata_layout.py`](scripts/gamedata_layout.py) and `src/binary/gamedata_layout.rs` (test-only), both of which probe newest-layout-first and fall back so a pre-2.01 install still reads.

2.01 ships **one real schema drift**, and it is not in iteminfo: `partprefabdyeslotinfo`'s per-slot `mask` widened from `[u8; 3]` to `[u8; 12]`, in both the slot and its 1.13-era extra layer. Byte consumption alone cannot place 9 inserted 0/1 bytes; what pins them *after* the original three is value distribution — occupancy falls monotonically from `mask[0]` (1,861 of 6,585 live slots) to `mask[11]` (140), and the historical "one mask bit per non-empty material name" correlation holds on `mask[0..3]` (39.4% exact) more than twice as often as on `mask[9..12]` (17.7%). The 3-byte `..._lookup_slot_mask` C ABI still hands out those first three unchanged. iteminfo, skill and the save body are all content-only: +3 items (6,810 → 6,813; keys 1005600 / 1005601 / 1005852), skill 2,046 → 2,061 entries with the format still `WithField58`, both byte-perfect on roundtrip. Row-count churn in 10 of 30 gamedata tables (houseinfo 12 → 22 is the largest relative move), and 2.01 also did a localization copy pass — two pinned mission titles changed (`Mission_Intro_Tutorial_I` "Unfamiliar Lands" → "Unfamiliar Land"; `Mission_MeetAlustain_Alustain_Wisdom` "Mysterious Man" → "A Mysterious Beggar"), which the `main_quest_chapter` curated table keys off.

The previous patch, **2.00, was the first *major* bump** (`meta/0.paver` 1/18/0 → 2/0/0 — the minor resets on a major bump, which is why `PARSER_TARGET_GAMEDATA_MAJOR` = 2 has to be read as a pair with the minor; 2.01 is `2/1/0/0xa31e5fcb`, so `PARSER_TARGET_GAMEDATA_MINOR` is now `1`). 2.00 shipped **two iteminfo drifts**: (1) `SubItem` gained `type_id == 18`, payload-free — the same renumbering 1.12 (tag 16) and 1.13 (tag 17) did, and in 2.00 *every* site that read 17 reads 18; (2) a new always-zero `u32` (`unk_pre_max_endurance_a`) inserted directly ahead of the 1.12-era `unk_pre_max_endurance`. +237 items (6,573 → 6,810, none removed). Skill is content-only (2,027 → 2,046 entries, format still `WithField58`); save body and all gamedata bridges clean apart from row-count churn (globalgameevent 188 → 191: 2.00 split `RoyalSupply` (0x424a) into four per-faction rows 0x4308–0x430b). The previous patch, **1.18, shipped exactly one iteminfo drift**: every `MergedPrefabVisualData` element gained a `u32` (`unk_pre_is_craft_material`) between `tribe_gender_list` and the 3-byte flag tail, reading the constant `0xeac5e173` — the "empty string" Jenkins sentinel — on all 12,274 elements (and on all 12,550 in 2.00). Before that, **1.17 was content-only over 1.16**: −9 items (the `Item_Set_*_Tier0_Reminiscence` block, keys 1004912–1004920), zero layout drift in any subsystem, `skill.pabgb` byte-identical. And **1.16** was the largest since 1.13 and the first ever to touch the skill parser: four iteminfo layout changes (head-side `inventory_info` removed; `DockingChildData.unk_post_summon_tag` removed — conditional on `docking_child_data` being present; a `u32 + u8 + CArray<UnkPreRespawnData> + u8` block inserted before `respawn_time_seconds`, which also **swapped order with `unk_pre_max_endurance`**; and `inventory_info_list: [u16; 9]` at the item end, absorbing the 1.13-era constant `unk_tail` as slot 8) plus one skill change (`PostBuff.unk_pre_damage_type: u8` before `damage_type` — this one broke 589 of 2,013 entries because the BuffData tail probe does not cover `PostBuff`). **Gotcha the 2.00 RE re-learned:** when a new `u32` lands inside an all-zero run, the byte diff cannot say *where* — every candidate position round-trips byte-perfectly. What settles it is which reading keeps the neighbours' known value distributions intact (`unk_pre_max_endurance` == `0x01000000` on exactly the 59 `Trade_*_PackedInVehicle` items; `respawn_time_seconds` ∈ {0, −1, 604800}) — the same argument the 1.16 swap rests on. See the "Validated patches" table in [`scripts/CLAUDE.md`](scripts/CLAUDE.md). Older patches need the sibling-install recipe in [`docs/historical-parser-setup.md`](docs/historical-parser-setup.md) — or the lighter `git archive HEAD` + `maturin build` + `pip install --target` route used for the 1.16 RE.

This file is intentionally a **minimal index** — detailed reference lives in the linked docs.

# Development
- **Build (Python wheel):** `maturin develop` (in a venv; the project uses `.venv/`) — auto-activates the `python` feature via `[tool.maturin]` in `pyproject.toml`. **The venv must be Python 3.12** — the wheel builds `abi3` for Python ≥ 3.12, so create `.venv` from a 3.12 interpreter (`py -3.12 -m venv .venv` or `C:\Users\<you>\AppData\Local\Programs\Python\Python312\python.exe -m venv .venv`), `source .venv/Scripts/activate`, then `maturin develop --release`. Run `export_for_ce.py` / any parsing from this same venv. **Stale-build gotcha — check this FIRST on a new patch, before suspecting schema drift.** Two independent copies can go stale: (a) a stray `crimson_rs` in the *global* Python 3.12 `site-packages` from an earlier `pip install`, and (b) **the venv's own `.pyd`** — `maturin develop` installs `crimson_rs` as editable, so `crimson_rs.__file__` points at the in-tree `python/crimson_rs/__init__.py` and *looks* current while the sibling `python/crimson_rs/crimson_rs.pyd` is whatever was last built. On 2026-08-09 that `.pyd` was 30 days old (a 1.13-era build) on a tree at 1.16. Either one silently mis-parses a new patch. So: `maturin develop --release` **before** any parsing run on a fresh patch, and sanity-check with `python -c "import crimson_rs, pathlib; p=pathlib.Path(crimson_rs.__file__).parent/'crimson_rs.pyd'; print(p.stat().st_mtime)"`. If you maintain the global install too, refresh it with `<Python312> -m pip install --force-reinstall --no-deps target/wheels/crimson_rs-*.whl`.
- **Build (C# / native):** `cargo build --release --features c_abi` → `target/release/crimson_rs.dll` (cdylib, ~1.2 MB) **and** `crimson_rs.lib` (staticlib, ~15 MB) in one pass. PyO3 is **not** linked; [`.cargo/config.toml`](.cargo/config.toml) statically links the MSVC CRT so the dll has zero transitive DLL deps. Downstream integration recipe (LoadLibrary vs NativeAOT single-file): [`docs/c-sharp-nativeaot-integration.md`](docs/c-sharp-nativeaot-integration.md).
- **Feature flags:** `default = []` (bare pure-Rust core, no FFI; dead_code allowed crate-wide via `cfg_attr` in `src/lib.rs`), `c_abi` (extern "C" surface), `python` (PyO3 + `extension-module`, so even the wheel never link-imports `python3.dll`). The two consumer features are independent and composable — enable both for the maximum surface (what CI lints).
- **Test:** `cargo test --lib`
- **Lint:** `cargo clippy --all-targets --lib --features c_abi,python -- -D warnings` (the union-of-all-features gate; CI also runs `cargo check --lib` for the bare-default build, see `.github/workflows/ci.yml`; `main` is branch-protected on the strict clippy check). **Local gotcha:** the `python` feature pulls PyO3 `abi3-py312`, so this aborts with `cannot set a minimum Python version 3.12 higher than the interpreter version 3.11` when the ambient `python` on PATH is older than 3.12 — prefix it with the 3.12 venv interpreter. **`PYO3_PYTHON` must be an ABSOLUTE path**: the pyo3 build script runs the interpreter from its own working directory, so a repo-relative `.venv/Scripts/python.exe` fails with `failed to run the Python interpreter at .venv/Scripts/python.exe (os error 3)` in both PowerShell and bash. Use `PYO3_PYTHON=D:/Github/crimson-rs/.venv/Scripts/python.exe cargo clippy --all-targets --lib --features c_abi,python -- -D warnings`. CI is unaffected (it pins 3.12); the `c_abi`-only build has no PyO3 and needs no Python.
- **Workflow:** develop on `dev` → PR to `main` → CI green → merge. That's the whole loop — **there is no publish step.** `.github/workflows/ci.yml` (clippy + cargo test) is the only workflow and the required check on `main`. The old `build.yml`, which rebuilt a Windows wheel on every push to `main` and republished it as a rolling `v1.0.<minor>.x` "Development Build" pre-release, was removed 2026-08-09 — traffic showed no external consumers, so there is nothing to bump on a new patch series and no release to retire. Consumers build from source (`maturin develop --release` for the wheel, `cargo build --release --features c_abi` for the native dll/lib). **Fork gotcha:** this is a fork of `potter420/crimson-rs`, so `gh` defaults PRs to the *upstream* parent (they fail with "No commits between main and dev / Head ref must be a branch"). Run [`scripts/setup-fork-guards.ps1`](scripts/setup-fork-guards.ps1) **once per clone** (pins `gh repo set-default bbfox0703/crimson-rs`, `remote.pushDefault=origin`, disables `git push upstream`), or always pass `gh pr create --repo bbfox0703/crimson-rs`. Never PR/push to upstream.

# Rules
- Ask before adding new dependencies to Cargo.toml.
- Binary format must roundtrip (read and write back identically).
- Custom types for binary serialization: `CString` (u32 len + len bytes — NO trailing NUL; this is what `iteminfo.pabgb` uses), `BString`-shape (u32 len + len bytes + u8 NUL terminator — used by `skill.pabgb` entry names + the PAPGT group_names_buffer; no shared Rust type yet, handled inline in `src/skill_info/mod.rs`), `optional<T>` (u8 flag + T if nonzero), `array<T>` (u32 count + count × T), `Variant` (u8 tag + match on tag).

# Binary Exploration
- Use `plcli` + `.hexpat` pattern files for binary format exploration, NOT Python scripts.
- Write partial hexpat patterns, test with `plcli run -i <file> -p <pattern.hexpat> -v -d`; iterate.
- Pattern files go in `references/`.

# Module map
`src/` is organized as: `binary/` (PAMT/PAPGT/PAZ/PALOC/trie/paver container formats + the test-only `gamedata_layout` archive-path resolver), `crypto/` (Jenkins checksum + ChaCha20), `item_info/` + `skill_info/` + `string_info/` + `character_info/` (byte-roundtrip parsers), `save/` (save header + crypto + body), and `c_abi/` (the feature-gated extern "C" surface). The full annotated per-file map is in [`docs/c-abi-surface.md`](docs/c-abi-surface.md).
